Retrieva — Markdown-native SRS Plugin 設計書

### 目的

Obsidian上で、Ankiに近いカード作成体験と学習体験を提供します。

ただし、Ankiのデータベース構造や同期方式は再現しません。カード本文、カード定義、学習状態、復習履歴はMarkdownファイルを正本とし、同期と競合解決はGitに委ねます。

プラグインが担当する範囲は次の四つに限定します。

1. カードの識別と読み込み
2. FSRSによるスケジューリング
3. 復習履歴の追記
4. レビュー画面と最低限の管理操作

Markdownの編集、リンク、埋め込み、添付ファイル、タグ、検索、バックリンク、ファイル履歴、同期はObsidianまたは他のプラグインへ任せます。

### 基本原則

**Markdownを正本とする**

復元不能な状態をプラグイン内部のDBやキャッシュだけに保存しません。キャッシュを削除しても、Vault内のMarkdownからカード一覧、現在状態、復習履歴を再構築できる必要があります。

**1カード1ファイル**

カード単位でMarkdownファイルを分けます。これにより、異なるカードを別端末で復習した場合にGit競合が発生しにくくなり、カード単位のリンク、タグ、検索、移動、削除も通常のObsidian操作で処理できます。

**原典とカードを分離する**

知識本文は通常のObsidianノートに置きます。カードファイルには本文を複製せず、Obsidianの埋め込みリンクで原典の見出しまたはブロックを参照します。

**履歴を正本とする**

カードの現在状態と復習履歴は、カードファイル内のJSONLイベント履歴を正本とします。通常の状態変更は末尾への追記として記録します。Undoと破損復元では、利用者の明示的な操作により既存行の削除、並び替え、parentの修正を行うことがあります。現在状態は、検証済みの線形履歴の末尾イベントに保存されたstateから取得します。

通常時の履歴は常に線形です。JSONLの物理的な行順をイベント順として扱い、各イベントのparentは直前行のeidとします（createdだけはparent: nullです）。追記専用のイベントDAGとしては扱いません。通常のレビューは末尾への一行追記、Undoは直前に追記したreview行の物理削除、破損復元は既存行の削除・並び替え・parentの書き換えという、三種類の操作だけを許可します。履歴が不整合な場合は自動修復せず、カードをレビュー対象から除外し、共通の破損復元画面で処理します。

**Gitに競合解決を委ねる**

ファイル同期とテキスト競合の解決はGitに委ねます。プラグインはGitのマージ機能を実装しません。Gitによる解決後のMarkdownを読み込み、JSONLの構文エラー、履歴の分岐、parent不整合などを通常のカード破損として検出します。Git競合マーカー専用の処理は作らず、結果としてJSONLが不正なら通常の構文エラーとして扱います。

**Obsidianの機能を再実装しない**

以下は実装しません。

- 独自Markdownエディタ
- 独自タグ管理
- 独自デッキファイル管理
- 独自検索エンジン
- 独自メディア管理
- 独自同期
- 独自バージョン管理
- 独自ノートリンク
- 独自カードブラウザ

**識別子は定数から導出する**

プラグイン名は「Retrieva」とします。接頭辞`retrieva-`を含むfrontmatterキー・タグ名・HTMLコメントマーカーをコード中に文字列リテラルとして直接書かず、一箇所の定数定義から参照し、識別子はすべてそこから導出します。

**コアロジックはホスト環境に依存しない**

イベント処理、状態導出、スケジューリング、検証などのコアロジックはObsidian APIに直接依存させません。Obsidianへの依存はFile adapterとUI adapterに閉じ込め、これらを差し替えることでCLIやTUIなど別の実行環境でも動作できる構成にします。詳細は「アーキテクチャ」を参照してください。

### アーキテクチャ

CLIとTUIを初期段階から想定するため、Obsidian非依存のコアと差し替え可能なadapter構成を維持します。ただし、コア自身がUI adapterを呼び出す構成にはしません。

```text
Obsidian plugin / CLI / TUI
          │
          ├─ File adapter
          ├─ UI adapter
          └─ Host application
                   │
                   ▼
                  Core
```

#### Core

Coreは次だけを担当します。

- カードMarkdownの解析
- イベントJSONLの解析
- イベントとstateの検証
- 線形履歴の確認
- 現在状態の取得
- FSRSによる次状態計算
- 回答候補の計算
- キュー構築
- 兄弟カードの判定
- 破損復元案の生成
- JSONLへ追加する行の生成

Coreは以下に依存しません。

- Obsidian API
- Node.jsのファイルシステムAPI
- DOM
- workspace leaf
- 標準入出力
- ターミナルUIライブラリ

時刻、タイムゾーン、生成済みIDは引数として渡します。

```ts
createReviewEvent({
  cardState,
  rating,
  preset,
  now,
  zone,
  eventId,
});
```

これにより、専用のClock adapterやID adapterを大規模に設計せず、テスト可能性を確保します。

#### File adapter

担当範囲は次です。

- Markdownファイルの列挙
- ファイルの読み込み
- ファイルの書き込み
- ファイル変更監視
- ファイル移動や削除の通知
- 埋め込み参照先の読み込み
- 見出しまたはブロックIDの解決

Obsidian版はVault APIとMetadataCacheを使用します。CLI・TUI版は通常のファイルシステムとMarkdown解析処理を使用します。

#### UI adapter

担当範囲は次です。

- スコープ選択
- レビュー表示
- 回答入力
- 設定表示
- 破損カード一覧
- 破損復元操作
- 原典またはカードファイルを開く操作

Obsidian版はworkspace leafとObsidian MarkdownRendererを使用します。CLI・TUI版は標準出力またはターミナルUIを使用します。

#### この分離の効果

同じコアロジックを、Obsidianプラグイン・CLIツール・TUIツールなど複数の実行環境で共有できます。File adapterとUI adapterの実装さえ用意すれば、コアやイベントスキーマを変更せずに新しい実行環境を追加できます。

### ファイルモデル

#### 原典ノート

原典ノートにはSRS固有の記法を要求しません。

```markdown
# 表

Hoge

# 裏

Hogehoge

# 補足

関連情報や出典。
```

見出しの代わりにObsidianブロックIDも利用できます。

```markdown
Hoge ^front

Hogehoge ^back
```

#### カードファイル

カードファイルは通常のMarkdownファイルです。

```markdown
---
retrieva-preset: default
tags:
  - retrieva-card
  - flashcards/example
---

![[原典ノート#表]]

<!--RETRIEVA-ANSWER-->

![[原典ノート#裏]]

<!--RETRIEVA-CARD {"v":1,"id":"019c84bd-7c6e-7dc1-a977-747042399f81"}-->

<!--RETRIEVA-LOG
{"v":1,"eid":"019c84bd-7c6e-7dc2-84c0-f1128caee903","type":"created","parent":null,"at":"2026-07-22T13:00:00+09:00","zone":"Asia/Tokyo","state":{"v":1,"phase":"new","due":null,"interval":0,"stability":null,"difficulty":null,"reps":0,"lapses":0,"learningStep":0,"suspended":false}}
RETRIEVA-LOG-->
```

役割は次のように分けます。

|部分|用途|
|---|---|
|frontmatter|Obsidianから検索・分類したい利用者向け情報|
|RETRIEVA-ANSWER|表面と裏面の境界|
|RETRIEVA-CARD|機械用の固定カードID|
|RETRIEVA-LOG|追記型の復習・操作履歴|

tags内のretrieva-cardタグは、Obsidian検索や他プラグインからカードファイルを識別するために使います。カードIDは利用者が通常編集する必要がないため、HTMLコメントへ保存します。

兄弟として扱うカードには、frontmatterへ`retrieva-sibling-group`を追加します。

```yaml
retrieva-preset: default
retrieva-sibling-group: 019c84bd-...
tags:
  - retrieva-card
  - flashcards/example
```

#### 兄弟グループ

兄弟関係の判定を次の規則へ変更します。

- 兄弟関係は`retrieva-sibling-group`の完全一致だけで判定する
- グループIDにはUUIDv7またはULIDを使う
- 表裏カードの同時生成時に共通IDを自動設定する
- グループIDがないカードは兄弟なしとして扱う
- 同じ原典ファイルを参照していても兄弟とはみなさない
- 複数の埋め込み先を解析して兄弟判定しない

原典ファイルや埋め込み参照から兄弟関係を推測するfallbackは廃止します。

#### 逆向きカード

逆向きカードは別ファイルとして作ります。

```markdown
---
retrieva-preset: default
retrieva-sibling-group: 019c84bd-...
tags:
  - retrieva-card
  - flashcards/example
---

![[原典ノート#裏]]

<!--RETRIEVA-ANSWER-->

![[原典ノート#表]]

<!--RETRIEVA-CARD {"v":1,"id":"019c84bd-7c6e-7dc3-814f-dc1bd9e909b8"}-->

<!--RETRIEVA-LOG
{"v":1,"eid":"019c84bd-7c6e-7dc4-9261-d93250ab3351","type":"created","parent":null,"at":"2026-07-22T13:00:01+09:00","zone":"Asia/Tokyo","state":{"v":1,"phase":"new","due":null,"interval":0,"stability":null,"difficulty":null,"reps":0,"lapses":0,"learningStep":0,"suspended":false}}
RETRIEVA-LOG-->
```

表裏の内容は原典ノートだけに存在します。カード側は参照方向だけを定義し、カードIDと兄弟グループIDは別の値です。

```text
カードA
  card id: A
  sibling group: G

カードB
  card id: B
  sibling group: G
```

#### frontmatterの責務

frontmatterには、利用者またはObsidianが扱う情報だけを置きます。

初期版で認識する要素は次の三つです。

```yaml
retrieva-preset: default
retrieva-sibling-group: 019c84bd-...
tags:
  - retrieva-card
```

tags内のretrieva-cardタグはカードファイルの識別に使います。それ以外のtags(flashcards/exampleなど)は、プラグインが通常のtagsをデッキ相当の分類として利用しますが、追加・変更・階層管理はObsidianに任せます。初期版では独自のdeckオブジェクトを持ちません。retrieva-sibling-groupは兄弟として扱うカードだけに設定します。

以下のような任意プロパティも、プラグインが破壊しないことを保証します。

```yaml
source:
  - "[[原典ノート]]"
aliases:
  - Hoge card
status: active
project: example
```

### イベントログ

#### JSONL形式

RETRIEVA-LOG内は、1行につき1つのJSONオブジェクトとします。

```
<!--RETRIEVA-LOG
{"v":1,"eid":"E1","type":"created","parent":null,...}
{"v":1,"eid":"E2","type":"review","parent":"E1",...}
{"v":1,"eid":"E3","type":"suspend","parent":"E2",...}
RETRIEVA-LOG-->
```

JSON配列にはしません。理由は次のとおりです。

- 末尾への追記だけで更新できる
- Git差分が小さい
- 複数端末の追加行を残しやすい
- 1行単位で破損を検出できる
- イベントIDによる重複除去が容易

JSONLの物理的な行順を正規のイベント順として扱うため、各行の`parent`は直前行の`eid`と一致します。通常のレビューでは既存行の並び替えや再整形を行いません。並び替えとparentの書き換えは、Undoによる末尾行の削除と、破損復元による明示的な修復操作だけの例外とします。

#### 共通イベント形式

```json
{
  "v": 1,
  "eid": "019c84bd-7c6e-7dc2-84c0-f1128caee903",
  "type": "review",
  "parent": "019c84bd-7c6e-7dc1-a977-747042399f81",
  "at": "2026-07-22T13:32:10+09:00",
  "zone": "Asia/Tokyo",
  "scheduler": "fsrs@1",
  "state": {}
}
```

|フィールド|意味|
|---|---|
|v|イベントスキーマのバージョン|
|eid|イベントの一意ID|
|type|イベント種別|
|parent|直前行のイベントのeid（createdだけはnull）|
|at|オフセット付きRFC 3339日時|
|zone|IANAタイムゾーン|
|scheduler|状態を計算したスケジューラ名と世代|
|state|イベント適用後の完全なカード状態|

イベントIDとカードIDにはUUIDv7またはULIDを使います。時刻順に並びやすく、複数端末でも中央採番を必要としないためです。

#### stateバージョン

stateにも独立したバージョンを追加します。イベントスキーマとstateスキーマを別々に更新できるようにするためです。

```json
{
  "state": {
    "v": 1,
    "phase": "review",
    "due": {
      "kind": "day",
      "date": "2026-08-12"
    },
    "interval": 21,
    "stability": 26.42,
    "difficulty": 4.83,
    "reps": 14,
    "lapses": 2,
    "learningStep": 0,
    "suspended": false
  }
}
```

各レビューイベントには、差分ではなく適用後の完全状態を保存します。これにより、将来FSRSライブラリやパラメータが変わっても、過去の現在状態を同じアルゴリズムで再計算する必要がありません。履歴から統計やFSRS最適化を行う際は、各レビューの評価と日時を使用します。

手動Buryを廃止するため、`buriedUntil`はstateの例、型定義、検証規則からすべて削除します。

#### イベント種別

MVPのイベント種別を次へ限定します。

|種別|用途|
|---|---|
|created|カード作成|
|review|Again、Hard、Good、Easyによる復習|
|suspend|カードの保留|
|resume|保留解除|
|reset|New状態へ戻す|

`bury`、`invalidate`、`resolve`、`checkpoint`、`extension`は削除します。将来必要になった場合は、イベントスキーマの新しいバージョンとして追加します。未知イベントを事前に許可する仕組みはMVPに入れません。

**reviewイベント**

```json
{
  "v": 1,
  "eid": "E2",
  "type": "review",
  "parent": "E1",
  "at": "2026-07-22T13:32:10+09:00",
  "zone": "Asia/Tokyo",
  "scheduler": "fsrs@1",
  "rating": "good",
  "durationMs": 3100,
  "state": {
    "v": 1,
    "phase": "learning",
    "due": {
      "kind": "instant",
      "at": "2026-07-22T13:42:10+09:00"
    },
    "interval": 0,
    "stability": 1.2,
    "difficulty": 5.4,
    "reps": 1,
    "lapses": 0,
    "learningStep": 1,
    "suspended": false
  }
}
```

**resetイベント**

resetイベントには適用後の完全stateを保存します。reps、lapses、intervalなどをリセットしたNew相当の状態になります。

```json
{
  "v": 1,
  "eid": "E5",
  "type": "reset",
  "parent": "E4",
  "at": "2026-07-22T15:00:00+09:00",
  "zone": "Asia/Tokyo",
  "scheduler": "fsrs@1",
  "state": {
    "v": 1,
    "phase": "new",
    "due": null,
    "interval": 0,
    "stability": null,
    "difficulty": null,
    "reps": 0,
    "lapses": 0,
    "learningStep": 0,
    "suspended": false
  }
}
```

Reset操作をMVPのUIへ出すか、コマンドだけにするかは別途決められますが、イベント形式には残します。

### 線形履歴の検証

JSONLの物理的な行順を正規のイベント順とします。正常な履歴は次の条件を満たします。

1. 最初のイベントは`created`
2. `created.parent`は`null`
3. `created`は一つだけ
4. 二行目以降の`parent`は直前行の`eid`
5. 各`eid`はファイル内で一意
6. 各行は正常なJSON
7. 各イベントは対応するスキーマを満たす
8. 各stateは対応するstateスキーマを満たす
9. 最後のイベントが現在状態になる

例：

```text
E1(created, parent=null)
E2(review, parent=E1)
E3(review, parent=E2)
E4(suspend, parent=E3)
```

次は破損です。

```text
E1(created, parent=null)
E3(review, parent=E2)
```

次も破損です。

```text
E1(created, parent=null)
E2A(review, parent=E1)
E2B(review, parent=E1)
```

DAGとして現在状態を解決せず、破損カードとして扱います。

### 破損復元画面

検証エラー、重複ID、履歴分岐、parent不整合は、すべて同じ破損復元画面で処理します。

#### 対象となる破損

最低限、次を検出します。

- JSONとして読めない行
- 必須フィールド不足
- 不正なイベント種別
- 未対応のイベントスキーマ
- 不正なstate
- `created`が存在しない
- `created`が複数存在する
- 最初のイベントが`created`ではない
- `parent`が直前行の`eid`と一致しない
- 同じ`parent`を持つ複数のreviewイベント
- 同一`eid`の重複
- 同一`eid`で内容が異なるイベント
- ファイル間でのカードID重複
- `RETRIEVA-CARD`、`RETRIEVA-LOG`、`RETRIEVA-ANSWER`の欠落または重複
- プリセット参照先の欠落
- プリセット定義の重複または構文エラー

#### 復元操作

破損復元画面で次の操作を許可します。

- 不正行の編集
- 不正行の削除
- 重複行の削除
- イベント行の並び替え
- `parent`の一括再生成
- 一方の分岐を採用して他方を削除
- 欠落カードIDの生成
- 欠落createdイベントの生成
- 重複カードIDを持つファイルの再発行
- 修復後の再検証

#### parentの修復

修復案の既定順序は次です。

1. `at`を絶対時刻として昇順
2. 同一時刻の場合は`eid`昇順
3. 利用者が必要に応じて手動で並び替え
4. 確定した順序に従って`parent`を再生成

先頭がcreatedであることを確認し、以降のparentを一行前のeidへ書き換えます。各イベントが適用後の完全stateを持つため、parentを張り替えるだけならstateの再計算は行いません。ただし、削除されたイベントの履歴情報は復元できません。

#### 分岐の解決

MVPでは、分岐した複数イベントのうち一つだけを採用します。

```text
E1
├─ E2A
└─ E2B
```

利用者がE2Aを採用した場合、E2Bの行を削除し、残ったイベント列のparentを再生成します。

「両方採用」はMVPから外します。両方を正しく採用するには、順序を決めたうえで後続レビューのstateを再計算する必要があり、そのレビュー時点の設定スナップショットが必要になるためです。

### Undo

Undoはreviewイベントの物理削除として実装します。対象は、現在のレビューセッション中に追加した直前のreviewイベント一件だけです。

削除条件は次です。

- 対象が現在の最終イベント
- 対象のtypeが`review`
- 現在のセッションが追加したイベント
- 追記後にカードファイルが外部変更されていない
- 追記後に別のイベントが追加されていない

条件を満たさない場合、Undoボタンを無効化します。

Undo時には次を行います。

1. 最終review行を削除
2. 直前イベントのstateを現在状態として再読込
3. キューを再構築
4. 兄弟カードの当日除外状態を再評価
5. 直前カードを必要に応じてレビューへ戻す

`invalidate`イベントは使用しません。

### Bury

手動Buryは設計全体から削除します。

削除対象は次です。

- `bury`イベント
- Buryボタン
- `buriedUntil`
- Buryの検証処理
- BuryのUndo処理
- Buryされたカードの件数表示
- Buryされたカードのキュー除外処理
- 受け入れ条件にあるBury
- MVP一覧にあるBury

兄弟カードの当日除外は残しますが、Buryとは別概念として扱います。

### 兄弟カードの当日除外

兄弟カードの除外はイベントとして保存せず、レビューキューから導出します。

同じ`retrieva-sibling-group`を持つカードのうち、一枚が端末のローカル日付で当日レビュー済みなら、設定に応じて他の兄弟を当日のキューから除外します。

```text
カードAをレビュー
      ↓
同じgroupのカードBを当日のキューから除外
```

複数ファイルへイベントを書き込む必要はありません。これにより、次が不要になります。

- 複数カードファイルの同時更新
- 兄弟Bury解除イベント
- 兄弟BuryのUndo
- 日付変更時の状態書き換え

既存の設定名がBuryを意味しているため、名称も変更します。

元：

```yaml
bury-new-siblings: true
bury-review-siblings: true
```

修正例：

```yaml
exclude-new-siblings-today: true
exclude-review-siblings-today: true
```

正式なfrontmatterキーは識別子定数から導出します。

Undoによって当日のreviewイベントが削除された場合、兄弟カードは次回のキュー再構築時に再び対象になります。

### 日時モデル

**イベント日時**

イベント日時は、オフセット付きRFC 3339形式で保存します。

```json
{
  "at": "2026-07-22T13:32:10+09:00",
  "zone": "Asia/Tokyo"
}
```

atはその瞬間を表し、zoneは学習日の境界や夏時間規則、および復習時に端末が使用していたタイムゾーンの記録を表します。

**分・時間単位の期限**

学習ステップや再学習ステップでは瞬間を絶対時刻として保存します。

```json
{
  "kind": "instant",
  "at": "2026-07-22T13:42:10+09:00"
}
```

期限判定は絶対時刻で行います。

**日単位の期限**

通常の復習カードでは、タイムゾーンを保存しないローカル日付とします。

```json
{
  "kind": "day",
  "date": "2026-08-12"
}
```

日単位の期限を午前0時のタイムスタンプへ変換して保存しません。期限判定は、実行中の端末のローカル日付を使います。

```text
端末の現在日付 >= due.date
```

旅行やタイムゾーン変更時にも、利用者が現在いる場所の日付を基準にします。兄弟カードの「当日レビュー済み」判定も、イベントの`at`を現在端末のタイムゾーンへ変換した日付で行います。

### プリセット

#### Markdown管理

プリセットは引き続きMarkdownファイルとしてVault内に置きます。

```markdown
---
retrieva-preset-definition: true
retrieva-preset-id: default
scheduler: fsrs
desired-retention: 0.9
maximum-interval-days: 36500
learning-steps:
  - 1m
  - 10m
relearning-steps:
  - 10m
exclude-new-siblings-today: true
exclude-review-siblings-today: true
---

# Default SRS preset
```

理由は次のとおりです。

- Gitで同期できる
- Vault内だけで復元できる
- CLIとTUIからも読み込める
- 利用者が直接編集できる
- Obsidian上で通常のファイルとして開ける

設定項目が少なく、専用設定DBを持たない設計にも一致します。初期版では次の設定だけを扱います。

- FSRS希望保持率
- 最大間隔
- 学習ステップ
- 再学習ステップ
- 当日の新規兄弟除外
- 当日の復習兄弟除外

新規カード上限や復習上限は後から追加できます。

#### プリセット参照

カード側の`retrieva-preset`は維持します。

```yaml
retrieva-preset: default
```

これはカードが現在どのプリセットを使うか決めるために必要です。プリセット定義側の`retrieva-preset-id`も、カードから参照するために必要です。

一方、reviewイベントにはプリセットIDを保存しません。IDが同じでも設定内容が変更されるため、過去設定の再現情報にはならず、誤解を招くためです。reviewイベントには次だけを保存します。

```json
{
  "scheduler": "fsrs@1",
  "state": {
    "...": "計算後の完全状態"
  }
}
```

#### 設定スナップショット

reviewイベントへプリセット設定全体を保存しません。現在状態はイベントの完全stateから復元できるため、通常のレビュー継続には過去設定が不要です。

この方針では次を扱いません。

- 過去の間隔計算の完全再現
- 当時の設定を使った履歴再計算
- 分岐レビューの両方採用
- 過去設定を使ったデバッグ再現
- 履歴全体の再スケジューリング

プリセット変更後は、次の回答から新しい設定を使います。過去イベントのstateは変更しません。

#### プレビューと確定

回答候補表示時と回答確定時で、同じプリセット内容を使う必要があります。

回答ボタン押下時にプリセットを再読込し、内容が変更されていた場合は次を行います。

1. 4回答の候補を再計算
2. 表示中の間隔を更新
3. そのクリックでは回答を確定しない
4. 利用者が更新後の候補を見て再度回答する

### カード発見

通常インデックスでは、カードタグを持つMarkdownだけを対象にします。

```yaml
tags:
  - retrieva-card
```

タグを削除したファイルは通常カードとして扱いません。

明示的なVault検証コマンドでは、次も検索対象にします。

- `RETRIEVA-CARD`マーカーを持つファイル
- `RETRIEVA-LOG`マーカーを持つファイル
- `RETRIEVA-ANSWER`マーカーを持つファイル

これにより、タグだけを誤って削除したカードは検証画面から発見できます。通常起動時にVault全体をマーカー検索する必要はありません。

### デッキとスコープ

専用のデッキモデルは実装しません。デッキ相当の分類には、既存のObsidian機能を利用します。

- タグ
- フォルダ
- frontmatterプロパティ
- Obsidian検索
- 他プラグインのクエリ

MVPでは一つのタグだけを指定可能にします。次は削除します。

- 複数タグ選択
- AND条件
- OR条件
- 複雑なタグクエリ
- フォルダとタグの複合条件

親デッキ、デッキID、デッキ専用DBは持ちません。フォルダ、現在の検索結果、選択されたファイル群による指定は、Queue filter拡張ポイントを使って後日追加します。保存済みショートカットも、一つのタグに対して一つの名前を付ける形にします。

```text
英語 → #flashcards/english
```

### デッキ選択画面

復習を開始する前に、対象範囲を選ぶ画面です。初期実装ではタグによる指定のみを扱います。

#### 保存済みのショートカット

登録済みのタグ条件には名前を付けて保存できます(例: 「英語」→`#flashcards/english`)。画面を開いた時点で、登録済みの各ショートカットの対象カード数をまとめて計算し、名前と件数を一覧表示します。行をタップすると、件数確認や開始ボタンを挟まず直接レビュー画面へ遷移します。

未登録の場合、この一覧は表示しません。

#### 新しいタグを指定

既存タグのサジェスト付き入力欄からタグを一つ選びます。選択すると対象カード数を表示し、「開始」ボタンでレビュー画面へ遷移します。「名前を付けて保存」にチェックを入れると、その条件を保存済みのショートカットに追加します。

### キュー構築

#### 対象カード

スコープ内のカードを次へ分類します。

- review可能
- future
- new
- suspended
- sibling excluded today
- invalid

invalidは通常キューへ入れず、破損件数として別枠表示します。

#### 優先順位

MVPでは次の順序に固定します。

1. 期限到来したlearning
2. 期限到来したrelearning
3. 期限到来したreview
4. new

learningとrelearningは内部的には別phaseとして保持しますが、同じ短期学習キューへまとめても構いません。その場合もdue時刻順に並べます。

#### 同一期限カードの順序

**learning・relearning**

1. `due.at`昇順
2. 同一時刻ならカードID昇順

**review**

1. `due.date`昇順
2. 同一日付ならカードID昇順

**new**

1. createdイベントの`at`昇順
2. 同一時刻ならカードID昇順

ランダム順序やfuzzはMVPでは追加しません。

#### セッション中に期限到来したlearning

セッション中に期限到来したlearning・relearningカードは再投入します。常時タイマーでキューを監視する必要はありません。次のタイミングで再構築します。

- 回答後
- Undo後
- Suspend後
- ファイル変更検出後
- プリセット変更検出後

回答後に短期学習カードが期限到来していれば、通常reviewやnewより先に表示します。キューが空になった時点で、未来のlearningカードを待つためにセッションを開き続けません。

```text
本日の復習は完了しました
次回予定: 10分後
```

#### newカード上限

元設計どおり、MVPでは新規カード上限を設けません。スコープ内の有効なnewカードはすべてレビュー候補になります。

#### 件数表示

次の形式にします。

```text
レビュー可能数 / スコープ内の全有効カード数
```

例：

```text
23 / 120
```

分子には、現在回答可能な次のカードを含めます。

- 期限到来したlearning
- 期限到来したrelearning
- 期限到来したreview
- new
- 当日兄弟除外されていないカード

分母には、スコープ内の正常な全カードを含めます。

- review可能
- future
- new
- suspended
- 当日兄弟除外中

invalidカードは分母へ含めず、別に表示します。

```text
23 / 120
破損カード: 3件
```

### セッション中の外部変更

表示中またはキュー内のカードが変更された場合は再読込します。

**カード本文だけが変更された場合**

- 表面と裏面を再描画
- stateと回答候補は維持

**イベント履歴が変更された場合**

- カードを再解析
- 現在stateを再取得
- 回答候補を再計算
- キューを再構築
- 破損していればカードを除外

**プリセットが変更された場合**

- 回答候補を再計算
- 表示間隔を更新
- 古い候補での回答確定を防止

**回答確定時**

回答ボタンを押したときにカードとプリセットを再読込します。表示時からスケジューリング入力が変わっていた場合、そのクリックではreviewイベントを書きません。最新状態で画面を更新し、再度回答を求めます。

### Markdown書き込み規則

通常レビュー時の規則は維持します。

- `RETRIEVA-LOG`終端直前へ一行だけ追加
- 既存JSONL行を変更しない
- frontmatterを変更しない
- 本文を変更しない
- ファイル全体を再整形しない
- キー順を固定
- 数値の丸め桁を固定
- 改行形式を維持
- 最終改行を維持

ただし、次は明示的な例外です。

**Undo**

- 最後のreview行を一行削除
- 他の行は変更しない

**破損復元**

- 不正行を削除または編集可能
- JSONL行を並び替え可能
- `parent`を書き換え可能
- 必要に応じてカードIDやcreatedイベントを発行可能
- frontmatterとカード本文は変更しない
- 修復対象は原則として`RETRIEVA-CARD`と`RETRIEVA-LOG`だけ

**書き込み前確認**

厳密なトランザクションは実装しません。最低限、次を行います。

1. ファイルを再読込
2. 表示時に保持した内容または最終イベントが変わっていないか確認
3. 変わっていれば書かずに再解析
4. プロセス内で同じカードへの重複書き込みを防止
5. 追記後にイベントが正常に存在することを確認

複数ファイルをまたぐトランザクションは不要です。兄弟カード除外をキューから導出するため、通常レビューでは一ファイルだけを書き込みます。

### レビュー画面

プラグイン独自UIはレビュー画面だけに限定します。必要な機能は次のとおりです。

1. 表面をObsidianのMarkdownレンダラーで表示
2. 答えを表示
3. 裏面を表示
4. Again、Hard、Good、Easyを選択
5. 各ボタンの次回間隔を表示
6. 回答時間を記録
7. 次のカードへ進む
8. Undo
9. SuspendまたはResume
10. 元カードファイルを開く

Markdown、数式、画像、音声、埋め込み、リンクの描画はObsidianへ任せます。独自Markdownレンダラーは作りません。

#### 画面構成

workspace leaf(タブ)として開き、モバイルでも動作する構成にします。ホットキーは設定せず、タップ・クリック操作のみで完結させます。

- 上部: レビュー可能数 / 全有効カード数、選択中のスコープ名、破損カードがある場合だけバナー
- 中央: 表面を表示し、タップ/クリックで裏面を表示
- 下部: Again/Hard/Good/Easyの4ボタン(タップしやすい大きさ)。各ボタン下に次回間隔を表示
- ヘッダー右上のアイコンボタン: Undo / Suspend または Resume / 元カードを開く

Buryボタンは削除します。

キューが空になったら「本日の復習は完了しました」と次回予定を表示します。セッションの統計サマリは表示しません。

#### 破損バナー

元の「検証エラー」と「履歴分岐」の二種類を、一つの破損カードバナーへまとめます。

```text
3件のカードに履歴または構文の問題があります
```

タップすると破損復元画面を開きます。レビュー画面内で枝を選択してresolveイベントを追加する処理は削除します。

### SuspendとResume

SuspendとResumeはイベントとして維持します。Suspendされたカードは次の扱いです。

- レビュー可能数には含めない
- 全有効カード数には含める
- キューには入れない
- future期限はstate内に保持する
- Resume後は保持していた状態から再開する

Suspendボタンを押した後はキューを再構築します。

### Reset

Resetは維持します。resetイベントには適用後の完全stateを保存し、reps、lapses、intervalなどをNew状態相当にリセットします(例は「イベント種別」を参照)。Reset操作をMVPのUIへ出すか、コマンドだけにするかは別途決められますが、イベント形式には残します。

### インデックス

インデックスは引き続き削除可能なメモリキャッシュとします。

保持する情報は次です。

- カードID
- ファイルパス
- プリセット参照
- 兄弟グループID
- 現在state
- 最終イベントID
- created日時
- 有効性
- エラー内容
- 対象タグ

分岐head集合のようなDAG用情報は不要です。イベント履歴が線形であることを確認し、最後のイベントだけを現在状態として保持します。

インデックスは正本ではありません。削除してもMarkdownから再構築できます。Vault内のファイル作成、変更、改名、削除を受けて、対象ファイルだけを再解析します。

既存のObsidian Spaced RepetitionはVault内のMarkdownを走査して状態を構築しています。新設計では全走査を起動時と明示的な再構築時に限定し、その後は差分更新します。永続キャッシュはMVPでは実装しません。カード数が増えて起動時間が問題になった場合にだけ、削除可能なキャッシュを追加します。

### カード作成

#### 通常カード

コマンド実行時に、現在のノートから表面と裏面の参照先を選択します。

入力例：

- 表面：[[原典ノート#表]]
- 裏面：[[原典ノート#裏]]
- 保存先：Cards/
- プリセット：default

生成物：

```markdown
---
retrieva-preset: default
tags:
  - retrieva-card
---

![[原典ノート#表]]
<!--RETRIEVA-ANSWER-->
![[原典ノート#裏]]
<!--RETRIEVA-CARD {"v":1,"id":"..."}-->
<!--RETRIEVA-LOG
{"v":1,"eid":"...","type":"created","parent":null,...}
RETRIEVA-LOG-->
```

#### 逆向きペア

「表裏カードを作成」コマンドでは、参照を入れ替えた2ファイルを生成し、二ファイルへ同じ兄弟グループIDを設定します。原典ノートにはカード生成用のメタデータを追加しません。生成済みカードの追跡はカードファイル側だけで行います。

#### 手動作成

利用者がテンプレートを複製して手動でカードファイルを作ることも許可します。カードIDまたはcreatedイベントがない場合は、破損復元または検証コマンドから発行できます。自動発行前に対象ファイルと変更内容を表示します。

### 設定画面

Obsidian標準のSettingsタブに準拠します。

- ショートカット一覧の追加・編集・削除(名前とタグ)
- プリセット一覧の表示と、該当Markdownファイルを開くボタン(値の編集はファイル側で行う)
- カード保存先フォルダの既定値
- リボンアイコンの表示切替
- 当日の新規兄弟除外
- 当日の復習兄弟除外

プリセット値そのものはMarkdown側で編集します。

### スケジューラ

初期版はFSRSだけを実装します。SM-2互換スケジューラは含めません。

スケジューラは、現在状態と評価から次回状態を計算する処理として分離します。関数シグネチャなど実装の詳細は実装担当に委ねます。この境界により、将来別のスケジューラを追加しても、ファイル形式、レビュー画面、イベントログを変更せずに済みます。

イベントには使用したスケジューラIDを記録します。

```json
{
  "scheduler": "fsrs@1"
}
```

既存イベントの状態は再計算しません。スケジューラ更新後のレビューから新しい実装を使用します。

### Obsidianへ委ねる機能

**カード編集**

カードファイルを通常のMarkdownとして編集します。専用カードエディタは作りません。

**原典編集**

原典ノートを通常どおり編集します。埋め込み内容はObsidianが解決します。

**カード検索**

次のようなObsidian検索を使います。

- `tag:#retrieva-card`
- `tag:#flashcards/example`
- `path:"Cards/"`

専用ブラウザは作りません。

**集計・一覧**

Dataviewなどからfrontmatterを参照できます。SRSの内部状態が必要な場合は、プラグインAPIから現在状態を取得できるようにします。

**同期**

Git、Obsidian Sync、クラウドストレージなどに任せます。プラグインは同期機構を持ちません。

**メディア**

画像、音声、PDF、Canvasなどの管理はObsidianに任せます。

### 拡張ポイント

初期設計で拡張可能にする箇所は次の三つです。

**Scheduler**

FSRS以外のアルゴリズムを追加できます。

**Card renderer**

初期版は表裏Markdownですが、将来Type AnswerやImage Occlusionを追加できます。

**Queue filter**

タグ、フォルダ、検索結果、任意条件からレビューセッションを作れます。

イベント種別を外部プラグインが自由に追加する仕組みはMVPでは提供しません。イベント形式の拡張が必要になった場合は、スキーマバージョンを上げてコア側で正式に対応します。

### 受け入れ条件

初期版は次の条件を満たした時点で完成とします。

1. カードファイルを別Vaultへコピーしても履歴と現在状態が失われない
2. プラグインデータを削除してもMarkdownから復元できる
3. 原典ノートを編集するとカード表示へ反映される
4. 表裏カードで本文が重複しない
5. 復習1回につきJSONL行が1行だけ追加される
6. 復習時にfrontmatterや本文が変更されない
7. ファイル移動後もカードIDと履歴が維持される
8. 同じparentを持つ複数イベント、parent欠損、parent不一致を検出し、対象カードを通常レビューから除外できる
9. 壊れたカードを通常レビューから除外できる
10. 数千カードで通常操作に支障がない
11. 他プラグインが追加したfrontmatterや本文を破壊しない
12. キャッシュなしで全状態を再構築できる
13. 破損復元画面でイベントを並び替え、parentを一括再生成できる
14. 分岐した履歴から一つの枝を選び、他方を削除して線形履歴へ戻せる
15. 修復後の現在状態は末尾イベントのstateと一致する
16. Undoで現在セッションの直前review行だけを物理削除できる
17. Undo後に兄弟カードの当日除外が再評価される
18. 日単位期限は実行端末のローカル日付で判定される
19. 分・時間単位期限は絶対時刻で判定される
20. 兄弟関係は兄弟グループIDだけで判定される
21. 同じ原典を参照していても、兄弟グループIDが異なれば兄弟とみなさない
22. 通常レビューでは一つのカードファイルだけが変更される
23. reviewイベントにはプリセットIDや設定スナップショットを保存しない
24. プリセット変更前のイベントstateは変更されない
25. プリセット変更後の回答から新設定が使われる
26. プリセット変更を回答確定時に検出し、古い候補で確定しない
27. 同一eid・異内容を破損として検出できる
28. 重複カードIDを検出できる
29. 不正JSONLを破損カードとして除外できる
30. Obsidian版、CLI版、TUI版が同じCoreを利用できる
31. Coreのテストで時刻、タイムゾーン、IDを固定値として指定できる
32. 通常レビューではfrontmatterと本文を変更しない
33. Undoと破損復元以外では既存JSONL行を変更しない

### 設計上の中心判断

このプラグインでは、カードファイルを学習単位とします。原典ノートが知識本文を持ち、カードファイルが出題方向、カードID、兄弟グループ、現在状態を含む線形イベント履歴を持ちます。

通常の復習操作ではJSONL末尾へ一行だけ追記します。履歴は通常時には線形であり、各イベントのparentは直前イベントを参照します。JSONLの構文エラー、parent不整合、履歴分岐などが発生した場合、カードをレビュー対象から除外し、利用者が破損復元画面から直接履歴を修復します。

過去のFSRS設定は保存せず、各イベントに適用後の完全stateを保存します。プリセット変更後は、次の回答から新しい設定を使用します。

プラグインはObsidianを置き換えません。Obsidian、CLI、TUIなどのホスト環境から、Markdownを反復学習カードとして扱うための共通コアを提供します。
